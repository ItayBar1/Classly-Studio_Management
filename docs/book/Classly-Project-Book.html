4. שם הפרויקט

Classly — פלטפורמת SaaS רב‑דיירית לניהול סטודיו כושר ובריאות.

5. רקע

עולם החוגים בישראל צומח ומתפתח משנה לשנה. יותר ויותר אנשים מחפשים מקום שבו יוכלו לשלב פעילות גופנית, אמנות ותנועה בחיי היומיום. עם זאת, מאחורי הקלעים מתנהל תהליך מורכב, ידני ומפוזר. הדבר יוצר קשיים הן מצד התלמידים, הנדרשים להתעסק ברישומים ותשלומים מסורבלים, והן מצד המורים והמנהלים, הנאלצים להשקיע זמן רב בארגון במקום להתמקד בהוראה ובפיתוח הקהילה.

תהליכים אלו גוזלים זמן יקר, פוגעים ביעילות ומקשים על כלל המשתתפים. מעבר לכך, פעילות ספורטיבית ואמנותית אינה רק עניין של בריאות פיזית — היא משפיעה ישירות על הנפש, יוצרת תחושת שייכות ותורמת לחוסן החברתי. לכן יצירת מערכת דיגיטלית מאוחדת שתפשט ותייעל את כל תהליכי הניהול בסטודיו היא לא רק פתרון טכנולוגי, אלא גם מענה חברתי וקהילתי חשוב.

6. מטרות המערכת

המערכת נועדה לספק פתרון דיגיטלי מלא לניהול חוגים וסטודיו — החל מהרשמות ותשלומים, דרך ניהול מערכות שעות ועד מעקב נוכחות. המטרה היא לאחד את כל התהליכים תחת פלטפורמה אחת, נוחה, יעילה ושקופה עבור מנהלים, מורים ותלמידים, תוך בידוד נתונים מלא בין סטודיואים (כל סטודיו הוא "דייר" מבודד שרואה רק את הנתונים שלו).

7. סקירת מצב קיים בשוק ובעיות קיימות

כיום, ניהול חוגים מתבצע לרוב בדרכים חלקיות ומסורבלות:

  • רישום ותשלומים ידניים או בהודעות פרטיות.
  • מערכות שעות שאינן מרוכזות וקלות לשינוי ללא תיאום.
  • חוסר שקיפות בתשלומים, הן מול הסטודיו והן מול המורים.
  • היעדר כלי דיגיטלי לניהול נוכחות.

התוצאה: עומס על המנהלים, חוסר סדר, טעויות אנוש ותחושת בלגן הפוגעת ביעילות הסטודיו ובחוויית המשתמש.

8. מה הפרויקט אמור לחדש או לשפר

  • אוטומציה של תהליכים — רישום ותשלומים מקוונים, וניהול מערכת שעות ונוכחות בצורה מרוכזת.
  • שיפור חוויית המשתמש — ממשק אינטואיטיבי ופשוט לתלמידים, מורים ומנהלים, בעברית ובכיווניות RTL.
  • ייעול הניהול הפנימי — פלטפורמה אחת לכלל הצרכים במקום שימוש בכלים מפוזרים.
  • תרומה קהילתית — חיזוק תחום האמנות והספורט, עידוד פעילות גופנית ויצירת חיבור בין אנשים.

10. בעיות צפויות במהלך הפיתוח ופתרונות

10.1 בעיות צפויות

  • עומסים על המערכת בתקופות רישום ותשלום.
  • ניהול שינויים במערכת שעות העלול לבלבל תלמידים ומורים.
  • שמירת מידע רגיש (פרטי תשלום ותלמידים).
  • ניהול מספר סטטוסים (הרשמה/תשלום) במקביל ושמירת עקביות.
  • בידוד מלא בין נתוני סטודיואים שונים.

10.2 פתרונות

  • שרת חסר‑מצב (stateless) הניתן להרצה בכמה עותקים מאחורי Nginx, וקונטיינרים עם restart policy תחת Docker — להפעלה מחדש אוטומטית בעת תקלה.
  • טרנזקציות (prisma.$transaction) לשמירת עקביות בפעולות מרובות‑טבלאות, ואידמפוטנטיות ב‑Webhook למניעת עיבוד כפול של תשלום.
  • אבטחת מידע — הצפנת סיסמאות (bcrypt), JWT בעוגיית HttpOnly, תקשורת HTTPS (דרך Cloudflare), ובידוד לפי studio_id.
  • ולידציה וניקוי קלט (Zod + sanitize‑html) ובקרת הרשאות בצד השרת בלבד.

12. שפות הפיתוח

שפת TypeScript היא שפת הפיתוח המרכזית במערכת ומשמשת בכל הרכיבים — בצד הלקוח, בצד השרת ובאינטגרציות החיצוניות. היא משלבת את הפשטות של JavaScript עם מערכת טיפוסים סטטית (strict: true) המונעת שגיאות ומייעלת את העבודה.

  • ב‑Front End היא משמשת עם React ליצירת ממשקים אינטראקטיביים.
  • ב‑Back End היא משמשת עם Express לכתיבת לוגיקה עסקית ו‑API.
  • SQL — שפת בסיס הנתונים היחסי (PostgreSQL); נגזרת ומנוהלת אוטומטית על‑ידי Prisma.

13. תיאור הארכיטקטורה הנבחרת

הארכיטקטורה שנבחרה מבוססת על הפרדה ברורה בין שלוש שכבות — צד לקוח (React), צד שרת (Express) ובסיס נתונים (PostgreSQL) — כשכולן רצות כשירותי Docker נפרדים תחת Docker Compose. צד הלקוח מוגש על‑ידי Nginx, המשמש גם כ‑reverse‑proxy ומעביר בקשות /api אל השרת. צד השרת עצמו בנוי בשכבות (Routes → Controllers → Services → Prisma), חסר‑מצב, ומתקשר עם בסיס הנתונים דרך Prisma ORM. הארכיטקטורה תומכת בפיתוח מהיר, באבטחה מובְנית וביכולת התרחבות.

15. השרת

השרת מבוסס Node.js (Express) וכתוב ב‑TypeScript. הוא רץ בקונטיינר node:20-alpine תחת Docker Compose, לצד קונטיינר postgres:18 וקונטיינר Nginx המגיש את צד הלקוח ומשמש כ‑reverse‑proxy לבקשות /api. גישה חיצונית מאובטחת מתאפשרת דרך Cloudflare Tunnel. השרת חסר‑מצב (stateless) ומתקשר עם בסיס הנתונים באמצעות Prisma ORM; כל שירות מוגדר עם מדיניות הפעלה מחדש אוטומטית בעת קריסה.

16. ממשק המשתמש / GUI

המשתמש ניגש למערכת דרך הדפדפן (Chrome / Edge / Safari) ללא צורך בהתקנת אפליקציה, כאפליקציית עמוד יחיד (SPA) שנבנתה ב‑React. הממשק עברי, בכיווניות RTL, ורספונסיבי — סרגל צד במחשב וניווט תחתון במובייל. האימות מתבצע מול השרת באמצעות עוגיית JWT.

17. ממשקים למערכות אחרות / API

המערכת מתממשקת לשירותים חיצוניים באמצעות API:

  • Stripe — סליקת תשלומים מאובטחת ויצירת כוונות תשלום; אירועי Webhook מאומתי‑חתימה (/api/webhooks/stripe).
  • Resend / Nodemailer — שליחת מיילים (הזמנות, איפוס סיסמה).
  • Loki + Grafana — איסוף לוגים מובְנים והצגתם בלוח בקרה.
  • Supabase — מאותחל בצד לקוח, שמור לאחסון קבצים עתידי.

המערכת בנויה במבנה מודולרי המאפשר הוספת ממשקים נוספים בעתיד.

19. שימוש במבני נתונים וארגון קבצים

בסיס הנתונים PostgreSQL משמש כמאגר המרכזי, עם טבלאות המייצגות ישויות: משתמשים, סטודיואים, סניפים, חדרים, קטגוריות, חוגים, הרשמות, נוכחות, תשלומים ועמלות. הקשרים הלוגיים: studio → branch → room → class → enrollment → attendance, וכן user (בעל תפקיד) ו‑payment. כל המפתחות הראשיים הם UUID, חותמות הזמן timestamptz, וכל טבלה תחומה ב‑studio_id. קבצי המערכת מאורגנים לפי שכבות — routes, controllers, services, middleware, schemas בצד השרת, וקומפוננטות לפי תפקיד + שכבת services בצד הלקוח. המבנה המלא מוצג בפרק תרשים ERD.

21. תיאור המרכיב האלגוריתמי‑חישובי

המרכיב האלגוריתמי‑חישובי המרכזי במערכת הוא תהליך ההרשמה לחוג והתשלום, לצד חישוב עמלות המדריכים ובקרת ההרשאות. בעת בקשת הרשמה מבצעת המערכת רצף בדיקות מסודר:

  1. אימות קיום החוג ושיוכו לסטודיו הנכון (בידוד רב‑דיירי).
  2. בדיקת קיבולת — current_enrollment < max_capacity.
  3. מניעת הרשמה כפולה — חיפוש הרשמה פעילה קיימת לאותו תלמיד וחוג.
  4. זיהוי חוג חינם (price = 0) והפעלה מיידית; אחרת יצירת הרשמה בסטטוס PENDING והפניה לתשלום.

עיבוד תשלום אידמפוטנטי: בעת קבלת Webhook מ‑Stripe, מתבצע עדכון מותנה בתוך טרנזקציה (updateMany … where status = 'PENDING') המבטיח שכל אירוע יעובד פעם אחת בלבד, גם אם נשלח שוב. חישוב עמלות מדריך נגזר מהתשלום ונרשם בטבלת instructor_commissions. בקרת הרשאות (RBAC) וסינון לפי studio_id מבטיחים שכל משתמש רואה ופועל רק על הנתונים המורשים לו.

7 צד שרת

Express + TypeScript בארכיטקטורת שכבות, מול PostgreSQL דרך Prisma

צד השרת נכתב ב‑Express וחושף REST API תחת הקידומת /api. הוא בנוי בשכבות, כאשר כל בקשה עוברת מסלול קבוע: שרשרת middleware (לוגים, אבטחה, אימות, הרשאה, ולידציה) ואז Controller → Service → Prisma → בסיס הנתונים.

7.1 ארכיטקטורת השכבות וזרימת הבקשה

השכבות ותפקידיהן:

  • Routes — מגדירות אילו מסלולי API קיימים ואילו middleware רצים על כל אחד.
  • Middleware — אחראי על נושאים רוחביים: לוגים, אבטחה, אימות זהות, הרשאה וולידציה.
  • Controller — קורא את הבקשה (req.body, req.params, req.studioId), קורא לשירות, ומעצב את התשובה.
  • Service — מכיל את הלוגיקה העסקית (קיבולת, תמחור, מעברי סטטוס) ואת שאילתות Prisma.
  • Prisma — שכבת הגישה לבסיס הנתונים, ממירה קריאות type‑safe ל‑SQL.

7.2 יתרונות ארכיטקטורת השכבות

1. הפרדת אחריות

כל שכבה אחראית על תחום אחד בלבד, מה שמפחית תלות ומאפשר לכל שכבה להתמקד בתפקידה.

2. תחזוקה קלה

קל לתקן באגים — כל נושא מטופל בשכבה אחת, ולכן קל לבודד את מקור התקלה.

3. גמישות להרחבה

הוספת פיצ'ר או ישות חדשה אינה דורשת שינוי בשכבות אחרות; המערכת גמישה לשינויים.

4. בדיקוּת

ניתן לבדוק כל שכבה בנפרד (למשל בדיקת שירות מול Prisma מדומה).

קובץ ה‑middleware המרכזי (app.ts)

סדר ה‑middleware קריטי: express.raw עבור /api/webhooks חייב לרוץ לפני express.json, כדי ש‑Stripe יוכל לאמת את חתימת הגוף הגולמי.

7.3 ה‑API המרכזיים

כל המסלולים תחת /api. מסלולים ציבוריים: /api/health, /api/auth/*, /api/webhooks/stripe. כל השאר דורשים אימות, ורובם גם הרשאת תפקיד.

קבוצת מסלולים תפקיד
/api/auth/* התחברות, הרשמה, me, התנתקות, שכחתי/איפוס סיסמה.
/api/courses/* ניהול חוגים (יצירה, עדכון, רשימה, חוגי מדריך/זמינים).
/api/enrollments/* הרשמה לחוג, הרשמות שלי, רשימת נרשמים, ביטול.
/api/payments/* היסטוריית תשלומים, יצירת כוונת תשלום.
/api/students, /api/instructors ניהול תלמידים ומדריכים.
/api/attendance/* סימון וצפייה בנוכחות.
/api/dashboard/* מדדים ללוח הבקרה (מנהל/מדריך).
/api/studios, /api/branches, /api/rooms ניהול סטודיו, סניפים וחדרים.
/api/webhooks/stripe קליטת אירועי Stripe (אימות חתימה, גוף גולמי).

7.4 הזדהות והרשאות

האימות מבוסס JWT בעוגיית HttpOnly בשם classly_token (JavaScript אינו יכול לקרוא אותה — הגנה מפני גניבת טוקן ב‑XSS). ה‑middleware authenticateUser מאמת את הטוקן, שולף את המשתמש מה‑DB, דוחה משתמש מושעה, ומצרף req.user ו‑req.studioId לבקשה. requireRole אוכף הרשאות לפי תפקיד.

בעת התחברות מוצלחת נחתם הטוקן ונשמר בעוגייה עם ההגדרות הבאות (תוקף 7 ימים; secure מופעל רק בייצור):

7.5 תפקידים (Roles)

תפקיד הרשאות
SUPER_ADMIN ניהול הפלטפורמה חוצה‑הסטודיואים והגדרות מערכת.
ADMIN ניהול מלא של הסטודיו שלו — סניפים, חדרים, חוגים, תלמידים, תשלומים, צוות והגדרות.
INSTRUCTOR לוח שיעורים, רשימת תלמידים בחוגיו, סימון נוכחות.
STUDENT עיון בחוגים, הרשמה ותשלום, צפייה בהרשמות שלו.
PARENT קיים בסכמה (רשומות ילדים) — שמור לשימוש עתידי.

7.6 טיפול בשגיאות מרוכז

בקרים ושירותים לעולם אינם כותבים res.status(500)... ישירות, אלא זורקים AppError שמטופל ב‑middleware מרכזי. כך התשובה ללקוח אחידה, והשגיאה נרשמת ללוג.

7.7 ולידציה וניקוי קלט

ה‑middleware validate(schema) מבצע שני שלבים לפני שהבקשה מגיעה ל‑Controller: (1) ניקוי תגיות HTML מכל שדה מחרוזת (למעט שדות רגישים כמו סיסמאות וטוקנים), ו‑(2) ולידציה מול סכמת Zod. הניקוי נמצא במקום אחד — כך שאף מסלול לא יכול "לשכוח" אותו.

7.8 התממשקות מול בסיס הנתונים (Prisma)

הגישה לבסיס הנתונים נעשית דרך Prisma. כל ישות מוגדרת כ‑model בסכמה, וממנה נגזרים גם הטיפוסים וגם ה‑SQL. דוגמה למודל ההרשמות, עם המפתחות הזרים והקשרים:

בידוד רב‑דיירי — studio_id בכל שאילתה

עיקרון מנחה: כל שאילתה תחומה ב‑studio_id. במקום findUnique({ where: { id } }) משתמשים ב‑findFirst({ where: { id, studio_id } }), ומתייחסים לכישלון כ‑404 — כך משתמש מסטודיו אחד לא יכול לגשת לנתוני סטודיו אחר גם אם ניחש מזהה.

טרנזקציות — הרשמה + תשלום יחד

פעולה הנוגעת בכמה טבלאות עוטפת אותן ב‑prisma.$transaction, כך שהן מתבצעות יחד (atomic). למשל, יצירת הרשמה ורישום שורת תשלום מתבצעים כיחידה אחת:

7.9 אינטגרציית Stripe ו‑Webhooks

תהליך התשלום: השרת יוצר PaymentIntent ומחזיר ללקוח clientSecret; הלקוח מאשר את התשלום מול Stripe; ולבסוף Stripe שולח Webhook מאומת‑חתימה לשרת, אשר מעדכן את התשלום וההרשמה בתוך טרנזקציה.

למה גוף גולמי? אימות חתימת ה‑Webhook של Stripe מתבצע על ה‑bytes המקוריים. לכן express.raw חייב לרוץ לפני express.json עבור /api/webhooks — אחרת החתימה לא תתאמת.

7.10 לוגים ובקרה (Pino + Loki)

כל בקשה מקבלת requestId ולוגר‑ילד ייעודי (req.logger) המצרף הקשר (כמו studioId, enrollmentId). הלוגים מובְנים כ‑JSON, נשלחים ב‑transport של pino-loki אל Loki, ומוצגים ב‑Grafana. לעולם אין רושמים סיסמאות, טוקנים או גוף בקשה מלא.

8 צד לקוח

React 19 + Vite + TypeScript · עברית RTL · מותאם למובייל

צד הלקוח הוא אפליקציית עמוד יחיד (SPA) ב‑React. הקומפוננטות מאורגנות לפי תפקיד, כל קריאות ה‑HTTP עוברות דרך שכבת שירותים אחת (api.ts), ומצב ההזדהות מנוהל ב‑App.tsx. כל הצילומים שלהלן נלקחו מהמערכת החיה.

8.1 מסכים מרכזיים במערכת

מסך התחברות והרשמה

נקודת הכניסה למערכת. ניתן לעבור בין "התחברות" ל"הרשמה", לאפס סיסמה, ולהירשם דרך קישור הזמנה. הטוקן נשמר בעוגיית HttpOnly, והמשתמש מנותב למסך המתאים לתפקידו.

לוח בקרה — מנהל סטודיו

לוח הבקרה של המנהל מציג מדדים מרכזיים (ממוצע נוכחות, שיעורים פעילים, הכנסות החודש, סך תלמידים) וגרפים (נוכחות שבועית ומגמת הכנסות) באמצעות ספריית recharts.

מערכת שעות

תצוגת לוח השיעורים השבועי וניהול חוגים. לחיצה על "שיבוץ שיעור חדש" פותחת מודל ליצירת חוג (ראו תמונה 8.16).

ניהול תלמידים

רשימת התלמידים של הסטודיו, עם חיפוש, רישום לחוגים וניהול. הנתונים מסוננים אוטומטית לפי הסטודיו של המנהל.

תשלומים וחשבוניות

ניהול התשלומים והצגת היסטוריית חיובים — סכום, שיטת תשלום, סטטוס והורדת חשבונית PDF. כפתור "תשלום חדש" פותח טופס תשלום מבוסס Stripe Elements.

ניהול הסטודיו

מסך הניהול מרכז את פרטי הסטודיו, הסניפים והצוות (מדריכים), כולל הזמנת אנשי צוות חדשים.

מסכי המדריך

המדריך רואה ממשק ממוקד: לוח בקרה אישי, לוח השיעורים שלו, רשימת התלמידים בחוגיו, ומסך נוכחות. כל מסך מציג רק את הנתונים הרלוונטיים למדריך המחובר.

ניהול ומעקב נוכחות (מדריך ומנהל)

מסך הנוכחות בנוי מרכיב תצוגה אחד משותף (components/common/AttendanceSections) המשרת הן את המדריך והן את המנהל, ללא כפילות קוד. השיעורים מחולקים לשלושה מקטעים נפתחים (אקורדיון שבו נפתח מקטע אחד בכל פעם) לפי סטטוס הדיווח: דווח / בתהליך / לא דווח. לחיצה על שיעור פותחת את חלון הדיווח (תמונה 8.13).

תצוגת המדריך (תמונה 8.10) מציגה רשימה שטוחה של שיעוריו בלבד. תצוגת המנהל (תמונה 8.11) מרכזת את נוכחות כל הסטודיו, עם סינון לפי סניף, מדריך, חדר, חוג, תלמיד וטווח תאריכים, והשיעורים בתוך כל מקטע מקובצים לפי סניף ← מדריך לסקירה נוחה.

בעת סינון לפי תלמיד התצוגה הופכת לממוקדת‑תלמיד: המקטעים מציגים את נוכחות אותו תלמיד (נוכח / איחור או באישור / נעדר), כך שהמנהל רואה מיד אילו שיעורים התלמיד החסיר.

חלון הדיווח (משותף אף הוא) מציג את תלמידי החוג עם הסימונים נוכח / חיסרון / איחור. ניתן לשמור כטיוטה בכל עת, אך כפתור "סיום דיווח" מושבת עד שכל התלמידים סומנו. כמו כן, ניתן לפתוח דיווח לשיעור רק החל מ‑15 דקות לפני תחילתו (שיעור עתידי מסומן כנעול), בעוד ששיעורי עבר נשארים פתוחים לדיווח.

מסכי התלמיד

התלמיד מקבל לוח אישי ומסך עיון בחוגים. בקטלוג מוצגים כל החוגים הזמינים — שם, מחיר, מועד, מדריך, חדר וקיבולת — והתלמיד יכול להירשם ולשלם. חוגים שהתלמיד כבר רשום אליהם מסומנים.

מנהל‑על (פלטפורמה)

מנהל‑העל מקבל תצוגת ניהול חוצה‑סטודיואים: ניהול סטודיואים, משתמשים פעילים והגדרות מערכת.

דף הנחיתה

דף השיווק הציבורי של המוצר — Hero, מחירים, מדריכים, גלריה ושאלות נפוצות — עם קריאה להתחברות/הרשמה.

תצוגת מובייל (Mobile‑first)

הממשק מותאם למסכים קטנים: במובייל סרגל הצד מתחלף בניווט תחתון (BottomNav), והתוכן מסתדר בעמודה אחת.

8.2 ניהול מצב (State)

אין store גלובלי. מצב ההזדהות חי ב‑App.tsx כ‑state מקומי, ומועבר בהורשה (props) לקומפוננטות. עותק מסונן של המשתמש נשמר ב‑localStorage (classly_user) לאתחול מהיר של ה‑UI, אך מקור האמת הוא השרת — בעת טעינה נקראת GET /api/auth/me דרך העוגייה.

8.3 שכבת השירותים (api.ts)

מופע axios יחיד עם withCredentials: true (שולח את העוגייה בכל בקשה). Interceptor של בקשות רושם לוג, ו‑interceptor של תשובות מטפל בשגיאת 401: אם פג תוקף הסשן, המשתמש מנותק והדף נטען מחדש. כל אובייקטי השירות (AuthService, CourseService, ...) הם עטיפות דקות מעליו.

8.4 ניתוב והרשאות בצד הלקוח

במצב מחובר, התוכן נקבע לפי activeTab. הפונקציה getComponentForTab מחזירה קומפוננטה שונה לכל שילוב של טאב ותפקיד — וכך אותו "טאב" מציג מסך מותאם לכל סוג משתמש. הסתרת טאבים היא קוסמטית בלבד; האכיפה האמיתית היא בשרת.

פריטי הסרגל עצמם מסוננים לפי תפקיד — כל פריט מגדיר אילו תפקידים רשאים לראותו:

8.5 ארגון קומפוננטות — "חכמה" מול "טיפשה"

הקומפוננטות מאורגנות לפי תפקיד (admin/, instructor/, student/, super-admin/), ומשתמשות בהפרדה בין קומפוננטה "חכמה" (מנהלת מצב ושולפת נתונים — למשל StudentManagement) לבין קומפוננטה "טיפשה"/מוצגת (מקבלת נתונים ב‑props ומציגה בלבד — למשל StatCard, ClassCard). כך נמנעת חזרה על קוד ונשמרת גמישות.

8.6 קומפוננטות גנריות משותפות ומודלים

בתיקיית components/common/ מרוכזות קומפוננטות לשימוש חוזר. BaseModal היא תשתית אחידה לכל החלונות הקופצים במערכת — היא נועלת גלילה, מציגה כותרת אחידה, ומקבלת תוכן וכפתורי תחתית.

8.7 אינטגרציית Stripe Elements (צד לקוח)

בצד הלקוח נטענת ספריית Stripe, וטופס התשלום מוצג באמצעות <PaymentElement /> בתוך <Elements>. פרטי הכרטיס נאספים ומאומתים מול Stripe ישירות — הם אינם נוגעים בשרת שלנו. אישור התשלום נעשה עם clientSecret שהתקבל מהשרת.

8.8 עיצוב RTL, Tailwind ומצב כהה

כל הממשק מוגדר dir="rtl" בשורש האפליקציה, והעיצוב נעשה עם TailwindCSS תוך העדפת utilities לוגיים (ms-*, me-*) על פני כיווניים. המערכת תומכת במצב כהה (Dark Mode) הניתן להחלפה מהסרגל, באמצעות מחלקות dark: של Tailwind (כפי שניתן לראות בקטעי הקוד שלעיל).

אבטחה בצד לקוח הסתרת טאבים וכפתורים לפי תפקיד היא לנוחות התצוגה בלבד. כל פעולה רגישה נאכפת מחדש בשרת — לעולם אין להסתמך על מצב הלקוח לצורכי אבטחה.

9 תהליכים מרכזיים במערכת

תרשימי רצף (Sequence) של התהליכים העיקריים

9.1 תהליך התחברות

המשתמש מזין פרטים; השרת מאמת מול ה‑DB, חותם JWT ושומר אותו בעוגיית HttpOnly; לאחר מכן הלקוח קורא ל‑/api/auth/me ומנתב לפי התפקיד.

9.2 תהליך הרשמה לחוג ותשלום

התהליך המרכזי של המערכת: התלמיד נרשם, נוצרת כוונת תשלום, הוא משלם דרך Stripe, ולבסוף Webhook מאמת‑חתימה מפעיל את ההרשמה בתוך טרנזקציה — כך שגם אם הדפדפן נסגר, ההרשמה תאושר.

9.3 תהליך הזמנת משתמש

מנהל מזמין מדריך/תלמיד; ההזמנה היא JWT הנושא role ו‑studio_id. בעת הרשמה עם הטוקן, התפקיד והסטודיו מוקצים אוטומטית.

9.4 תהליך סימון נוכחות ומעקב

המדריך מסמן נוכחות למפגש; אילוץ ייחודיות על (enrollment_id, session_date) מונע סימון כפול לאותו מפגש, והנתונים משמשים בהמשך לחישוב עמלות. דיווח נפתח רק החל מ‑15 דקות לפני תחילת השיעור; ניתן לשמור כטיוטה (מצב IN_PROGRESS) בכל שלב, ו"סיום דיווח" (COMPLETED) מתאפשר רק לאחר שכל התלמידים סומנו.

סקירת המנהל. בנוסף לדיווח המדריך, המנהל צופה בנוכחות כלל הסטודיו דרך נקודת קצה אחת (GET /api/attendance/overview) שמחזירה את אותם נתונים בשני מצבים: ברירת מחדל — תצוגת מפגשים מקובצת לפי סניף ומדריך; ובהעברת studentId — תצוגה ממוקדת‑תלמיד. שני המסכים (מדריך ומנהל) צורכים את אותו רכיב תצוגה משותף, כמתואר בפרק "צד לקוח" (תמונות 8.10–8.13).

9.5 תהליך איפוס סיסמה

נשמר רק hash של הטוקן (לעולם לא הטוקן הגולמי), עם תוקף שעה. האיפוס עצמו והסימון "נוצל" מתבצעים בתוך טרנזקציה, ולאחריו המשתמש מחובר אוטומטית.

10 סיכום ומסקנות

פרויקט Classly פיתח את יכולתנו לתכנן ולממש מערכת ווב מלאה (full‑stack) מהאפס — מהקמת בסיס נתונים ותכנון ברמת ארכיטקטורה, דרך פיתוח צד שרת וצד לקוח והחיבור ביניהם, ועד הרצת המערכת כולה בסביבת קונטיינרים אחת.

במהלך הפרויקט התמודדנו עם מספר אתגרים מרכזיים:

  • בידוד רב‑דיירי — הבטחה שכל סטודיו רואה אך ורק את נתוניו, באמצעות סינון עקבי לפי studio_id בכל שאילתה.
  • תשלומים מקוונים — אינטגרציה עם Stripe, כולל אימות חתימת Webhook על גוף גולמי ושמירה על אידמפוטנטיות מול שליחות חוזרות.
  • עקביות נתונים — שימוש בטרנזקציות כדי שפעולות מרובות‑טבלאות (הרשמה + תשלום) יתבצעו כיחידה אטומית.
  • ממשק עברי RTL ומותאם מובייל, עם תמיכה במצב כהה.
  • תזמור Docker — הרצת כל השירותים (DB, שרת, לקוח, לוגים) בפקודה אחת, בסביבה זהה לפיתוח ולייצור.

למדנו לעומק טכנולוגיות מודרניות — TypeScript, Prisma, React, Stripe, Docker ו‑Loki/Grafana — וכן עקרונות הנדסת תוכנה כמו ארכיטקטורת שכבות, הפרדת אחריות, קומפוננטות גנריות ואבטחה כברירת מחדל.

שיפורים עתידיים

כחלק מהסתכלות קדימה, זיהינו מספר כיווני שיפור שיחזקו את המערכת:

שיפור תועלת
שער בדיקות ב‑CI הרצת typecheck ובדיקות אוטומטית בכל PR לפני מיזוג ל‑main.
מודול TenantScope ריכוז סינון ה‑studio_id במקום אחד — כך אי‑אפשר "לשכוח" אותו בשאילתה.
טבלת webhook_events מניעת עיבוד כפול של אירועי Stripe ברמת מזהה האירוע (dedup מלא).
Refresh Tokens חידוש סשן שקוף ללא טעינה מחדש של הדף לאחר פקיעת הטוקן.
אינדקסים ב‑DB אינדקסים על studio_id, status ועמודות זמן — לשיפור ביצועים בנפח גדול.
i18n חילוץ מחרוזות עברית והוספת אנגלית להרחבת קהל היעד.

לסיכום, Classly מדגימה כיצד ניתן לבנות פלטפורמת SaaS רב‑דיירית, מאובטחת ונוחה לשימוש, תוך שימוש בכלים מודרניים ובעקרונות הנדסיים מבוססים — תוצר שאנו גאים בו ושממנו למדנו רבות.
